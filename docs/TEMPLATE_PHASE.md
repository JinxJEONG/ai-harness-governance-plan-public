# Phase 문서 템플릿

모든 `docs/phases/PHASE_N_*.md`는 아래 8개 절을 같은 순서와 같은 제목으로 갖는다.
절을 생략하거나 이름을 바꾸지 않는다. 해당 절에 내용이 없으면 "없음"과 그 근거를 쓴다.

phase 승인 단위는 파일 단위와 1:1로 대응한다. 한 phase의 승인·거절 판단에 필요한
모든 정보는 그 phase 파일 하나와 그 파일이 명시적으로 링크한 문서 안에 있어야 한다.

## 작성 규칙

| 규칙 | 내용 |
|---|---|
| R-01 | 종료조건은 반드시 실행 가능한 명령 또는 검사 가능한 파일 경로로 표현한다. "확인한다", "검토한다" 같은 판단 동사만으로 종료조건을 적지 않는다. |
| R-02 | 실행 절차의 각 단계는 read-only / additive / mutating 중 하나로 표시한다. mutating 단계는 대상 경로와 소유권(`kit-owned` / `merge-owned` / `project-owned` / `generated`)을 함께 적는다. |
| R-03 | 증거 경로를 명시한다. 어떤 파일에 무엇이 기록되어야 종료조건이 충족되는지 적는다. |
| R-04 | 미해결 사항은 문서 안에 `TODO`로 남기지 않는다. `HARNESS_GOVERNANCE_MIGRATION_PLAN.md`의 "결정 원장 > 미결 항목"에 올리고 여기서는 그 항목 ID를 참조한다. |
| R-05 | 추측한 사실과 실측한 사실을 구분한다. 실측값은 수집 시각과 수집 명령을 함께 적는다. |
| R-06 | 이 저장소에는 validator 스크립트를 두지 않는다. 검증은 사람이 문서를 읽고 명령을 실행해 수행한다. |

## 표준 절

### 1. 목적

이 phase가 무엇을 성립시키는지 3문장 이내로 적는다. 다음 phase가 이 phase 없이는
왜 불가능한지 한 문장으로 밝힌다.

### 2. 전제조건

이 phase를 시작할 수 있는 조건을 검사 가능한 형태로 나열한다. 선행 phase의 종료조건,
필요한 승인, 필요한 도구(Ruby, Docker, git)를 포함한다.

### 3. 산출물

이 phase가 끝났을 때 존재해야 하는 파일과 상태를 나열한다. 각 산출물에 소유권을 표시한다.

### 4. 실행 절차

번호가 붙은 단계로 적는다. 각 단계에 R-02의 read-only / additive / mutating 표시를 붙인다.

### 5. 검증 명령

복사해 그대로 실행할 수 있는 명령을 적는다. 각 명령에 기대 결과(exit code, 출력 패턴)를
함께 적는다.

### 6. 종료조건

R-01을 만족하는 목록으로 적는다. 이 목록이 곧 승인 체크리스트다. 각 항목에 대응하는
검증 명령 번호와 증거 경로를 연결한다.

### 7. 롤백

종료조건을 충족하지 못했을 때 어떻게 이전 상태로 되돌리는지 적는다. 되돌릴 수 없는
단계가 있으면 그 단계를 명시하고, 그 단계 앞에 어떤 checkpoint가 필요한지 적는다.

### 8. 이 phase가 승인하지 않는 작업

`HARNESS_GOVERNANCE_MIGRATION_PLAN.md` §14를 상속한다. 이 phase에서 특별히 금지되는
작업을 추가로 나열한다.
